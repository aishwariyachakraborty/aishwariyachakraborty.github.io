DL Compilers Series - 3 - Triton

Published in April 2026

To understand triton, let's first recap the GPU architecture and programming model briefly.
Basics of GPU architecture:

  • Many (thousands of) cores, which can work at the same time.
  • GPU has repeated tiles of hardware blocks (of cores) - each block is analogous to streaming multiprocessors (SMs) or cooperative thread array (CTAs)
  • Each SM has multiple identical vector compute units (CUDA cores) and matrix compute units (tensor cores).
  • Vector compute units follow SIMT: 32 threads form a warp. Each thread in the warp works on the same instruction at the same time but independently. All threads in a warp have the same program counter.
  • Matrix compute units are different: Each thread works on a part of the input data/matrix. Threads work collaboratively to reach final output. Each warp viewed as a single logical unit.
  • Memory hierarchy:
    • One DRAM which is global, bigger in size (~80GB in A100) but lower bandwidth (~1.5 GB)
    • One SRAM local to each Streaming Microprocessor (SM), smaller in size (~MBs) but high bandwidth.
    • All data must be brought to the SRAM before being operated on.



Triton is a programming language for GPUs, which currently supports NVIDIA and AMD GPUs. Unlike CUDA, where you define the behavior of a single thread, Triton kernels define operations on blocks of data. At present, triton code does not run on CPU. Triton is open source, and is ~90% as fast as CUDA.

Triton Programming Model
  • Each kernel has multiple instances, each called a program defined by a PID. The kernel for each program is same, only the data is different, and determined based on the PID.
  • Atleast one pogram per SM.
  • All the instructions + the data on which the cores in the SM will work on must fit into the available SRAM of the SM, otherwise it will throw error. Number of PIDs on a single SM = Amount of SRAM // SRAM required per PID
  • If two different kernels share the same data, the data is loaded only once.
  • Thread is the smallest unit of actual computation / performs single FLOP.
    • Warp is the smallest possible group of threads (typically 32 in Nvidia GPUs) which perform the same program. (i.e., WARP can work on 32 entries of a tensor at a time)
    • Many threads share a smaller number of cores via fast scheduling.
    • For max parallelization, make sure all threads in a warp has data to work with (i.e., split data into multiples of 32), otherwise the remaining threads in the warp will be idle.
Triton Code:
  • Grid - How many instances of the kernel to be created (total size of data to create / BLOCK_SIZE)
  • BLOCK_SIZE - How much data one program instance processes
  • @triton.jit tells python that this is not a regular function but a triton kernel which needs to be compiled on GPU. we always pass pointers to the input and outputs.
  • tl.constExpr - compile time argument which wont change much. If this changes, entirely new kernel will be created.
  • Rough Structure of Kernel:
    • Define the PID usint tl.program_id/li>
    • Define the block start in terms of PID, and offsets in terms of block start and block size
    • Create the mask to account for when to end the offset for final block
    • Load input data from DRAM to SRAM using tl.load with mask and other=None/-inf/inf as appropriate (set the unused entries to some value)
    • Calculate output
    • Write output data back to DRAM using tl.store and mask to make sure only correct data is there.
  • Get properties of the device: triton.runtime.driver.active.utils.get_device_properties(DEVICE.index) {'max_shared_mem': 166912, 'max_num_regs': 65536, 'multiprocessor_count': 108, 'warpSize': 32, 'sm_clock_rate': 1410000, 'mem_clock_rate': 1593000, 'mem_bus_width': 5120}
  • The number of programs that can be assigned to an SM is limited by the SRAM occupancy as well as the register occupancy.
    • Pipelining: Even within a single program, instead of performing the steps sequentially, GPU can do memory reads while doing FLOPs or it can do memory writes while doing other operations, if there are no dependencies between them. 'num_stages' allows us to specify how many ops the GPU should do.
Dump all IRs: TRITON_ALWAYS_COMPILE=1 MLIR_ENABLE_DUMP=1 TRITON_DISABLE_LINE_INFO=1 NVPTX_ENABLE_DUMP=1 Fused softmax kernel example from tutorial: 
                
    @triton.jit
    def softmax_kernel(
        input_ptr, output_ptr,
        input_row_stride, output_row_stride,
        n_rows, n_cols,
        BLOCK_SIZE: tl.constexpr,
        num_stages: tl.constexpr,
    ):

        row_start = tl.program_id(0)
        row_step = tl.num_programs(0)

        for row_idx in tl.range(row_start, n_rows, row_step, num_stages=num_stages): 
            row_start_idx = input_ptr + row_idx * input_row_stride
            col_offsets = tl.arange(0, BLOCK_SIZE)
            
            row = tl.load(row_start_idx + col_offsets, mask = col_offsets<n_cols, other=-float('inf'))
            row_minus_max = row - tl.max(row, axis=0)
            numerator = tl.exp(row_minus_max)
            denominator = tl.sum(numerator, axis=0)
            softmax_output = numerator/denominator

            output_row_ptr = output_ptr + row_idx * output_row_stride
            
            tl.store(output_row_ptr+col_offsets, softmax_output, mask = col_offsets<n_cols)
  • tl.program_id(axis) returns the index of the current instance along a given dimension.
  • Here num_stages tells GPU to do pipelining between ops in the for-loop.
  • In case the number of rows > num of programs being instantiated, then each PID will get more than one row. And those rows wont be the one right after. (The one right after would be assigned to the next PID.) We have to jump down "row_step" rows to get to the next one.
  • We have to use mask while loading as as BLOCK_SIZE may be > n_cols, which would lead to reading the values out of range of the data.
  • We have to use mask while storing as it prevents us from overwriting any unwanted data.
